# Release checklist (smoke test)

Run this on the **test server** (admin.vioratech.in, the store's own domain) after `dev` has
deployed and **before** opening the `dev` → `main` release PR. Unit tests check each piece on
its own; this checks the whole flow on a real server, real DNS, real email and real storage,
which is where the 2026-10-05 bugs hid (issues #255–#266).

## Before the smoke test — local gates

Run these locally first; any failure blocks the release the same way a smoke row does:

- `bun run audit` — dependency CVE gate (`scripts/security-audit.ts`). Fails on a **high/critical
  advisory whose fix our declared version floor can still resolve below** (a real direct exposure).
  This is the gate that would have caught the Sep-2026 `better-auth` OAuth account-takeover the day
  it was disclosed — a point-in-time audit cannot, because the CVE can land after the audit. If it
  fails, bump the version (or triage the advisory id into `ALLOW` with a reason). Transitive and
  already-patched copies print as warnings, not blockers.
- `bun run typecheck` and `bun run test` — the tsc + vitest pass on `dev` before the release.

## First: the checkout smoke test

Before anything else, run the scripted checkout from your machine against the store you are about
to release (the live store, the test server's store or a local storefront):

```bash
bun run smoke:checkout -- --base https://waimers.koomerce.app
```

It walks a guest, on a desktop and a phone viewport, through: home, a collection, a search, a
misspelt search, a product's **Add to cart**, the cart (line with image and price), then checkout:
cookies, any popup, guest contact (`success@simulator.amazonses.com`, `9999999999`), and the
address with PIN **131001** (Haryana) and **400001** (Maharashtra). For each PIN the city and state
must fill in and **Shipping** must show at least one option; "We do not ship to …" or "We cannot
deliver to …" fails it (the 21 Oct bug, which only showed at that step). It stops when **Payment**
lists a way to pay and never presses Pay, so no order is placed.

It prints a pass/fail table and exits non-zero on any failure, with full-page screenshots of each
failed step in a temp folder (the path is printed). Options: `--viewport desktop|phone`,
`--query <word>` (search word; default: a word from an in-stock product), `--pin 744101:AN` (also
check a PIN a shopper reported). A failing row blocks the release like any row below.

First run on a machine: `bunx playwright install chromium-headless-shell`. It runs on Node, not
Bun: Bun on Windows cannot drive Playwright's browser pipe and the launch hangs.

## Manual checklist

Click through each row. Tick it only if the **Expect** column is exactly what you saw. A failing
row becomes a GitHub issue (label `bug` + `test-server`) and blocks the release.

| # | Flow | Steps | Expect |
| --- | --- | --- | --- |
| 1 | Apps are up | Open the admin and the store's primary domain | Both load over HTTPS, no browser warning |
| 2 | Owner sign-in | Log out, log in with the owner email | Code arrives by email within a minute; lands on Home |
| 3 | Staff invite | Settings → Staff → invite a verified test address with a non-owner role | Invite email arrives; Pending invites lists it |
| 4 | Staff sign-in | Open the invite as that person, accept, log in | Lands on Home of the store (no store-picker loop) |
| 5 | Store links | Click **View store**, a product's "View on store", and a theme **Preview** | All open on the store's primary domain, never `shop.vioratech.in` |
| 6 | Custom domain | Settings → Domains: every domain shows **Active**; open each | Each opens the shop; non-primary ones redirect if set |
| 7 | Storage | Content → Files → Storage → **Test connection**; upload one image | "Connected to bucket …"; the image shows on the store |
| 8 | Import | Apps → Shopify importer → **What's left to import**; copy one small type | Run moves (progress bars change), finishes Completed or lists clear problems; never "Running" with nothing moving |
| 9 | Checkout (test mode) | Add a product to cart, check out with the payment provider's test details | Order appears in Orders; confirmation email arrives |
| 10 | Order emails | Mark that test order fulfilled, then delivered | Shipping/delivery emails arrive with links on the store's domain |
| 11 | Worker health | Dokploy → worker → Logs | Heartbeat every minute; no repeating error lines |
| 12 | Dark mode + phone | Toggle dark mode; open admin Home and the store on a phone | Top bar readable; no sideways scrolling |

## After the checklist

- All rows ticked → open the release PR `dev` → `main` and paste the ticked table into its body.
- Any row failed → issue on GitHub, fix PR into `dev`, re-run the failed rows (and any row the fix
  touches) after the next deploy.

## Bugs

Every bug found anywhere (test server, local, a merchant) is one GitHub issue, so nothing is lost
between sessions. On the test server, testers use **Report a bug** (account menu or the button at the
bottom left), which files the issue for them with the page, store, browser and an optional
screenshot attached; see [Bug reports](/developer-docs/operations/bug-reports). Labels: `bug`, plus `test-server`, `importer` or `deploy` where they fit. The fix
PR says `Fixes #<n>` so the issue closes when it merges into the default branch (`dev`).
