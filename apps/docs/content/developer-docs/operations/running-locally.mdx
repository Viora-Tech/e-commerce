# Running locally

Turborepo + bun. Apps: `apps/admin` (Next, port **3200**), `apps/storefront` (Next, **3100**),
`apps/worker` (Bun + BullMQ, **4100**), and this docs site, `apps/docs` (**3500**). Background
agents should use other ports (3700+) and stop them when done.

## 1. Environment

Copy the root `.env.example` to `.env` and fill in the required keys (`packages/config/src/env.ts`
is the source of truth for which keys each app needs). At minimum:

```sh filename=".env"
DATABASE_URL=              # Postgres, `app` role
DATABASE_URL_OWNER=        # Postgres, owner role — migrations, seeds
REDIS_URL=                 # BullMQ queues and visitor counters
AUTH_SECRET=                # Better Auth signing secret, 32+ chars
```

Every app reads it via `bun run --env-file=../../.env`.

## 2. Infrastructure

```sh filename="Terminal"
docker compose up -d --wait     # Postgres 17 + Dragonfly
```

## 3. Install, migrate, seed

```sh filename="Terminal"
bun install
bun run db:migrate              # dev database
bun run db:seed                 # real Waimers catalogue (72 products)
bun run db:seed:demo             # 60+ orders, customers, drafts, abandoned carts
bun run db:seed:demo:collections
```

## 4. Run

```sh filename="Terminal"
bun run dev                     # admin, storefront, worker
bun run dev:docs                # this docs site, on :3500
```

Admin: `http://localhost:3200`. Storefront: `http://localhost:3100`. Worker:
`http://localhost:4100`. Docs: `http://localhost:3500`.

## Signing up to create a new store

`MERCHANT_SIGNUP_MODE` (`packages/config/src/env.ts`) gates who may create their own store from
`/onboarding`: `invite` (default) or `open`. In `invite` mode, a person with no store yet who
signs in sees "Signups are invite-only for now" unless their email has a live invite. There is
no platform admin UI yet, so invites are issued from the CLI:

```sh filename="Terminal"
bun run platform:invite owner@example.com
```

This prints a link (`<ADMIN_URL>/onboarding?...`); send it to the merchant. Access is granted by
matching their signed-in email to a live invite, not by the link itself, so it is a convenience,
not a secret. Set `MERCHANT_SIGNUP_MODE=open` in `.env` for local development if you want to skip
this and let any signed-in email create a store. `PLATFORM_STORE_DOMAIN` (default
`waimers.store`) is the base domain new stores' primary domain is built from
(`<slug>.<PLATFORM_STORE_DOMAIN>`); every new store also gets `<slug>.localhost` outside
production. The service behind all of this is `createStore`
(`packages/core/src/onboarding/service.ts`).

Existing staff invitations to join an existing store (Settings → Staff, `/accept-invitation/[id]`)
are unaffected by this gate - they always work.

### The guided flow and the waitlist

`/onboarding` is a client-side wizard (`apps/admin/src/components/onboarding/onboarding-wizard.tsx`),
one question per screen: store name and address → what you sell → where you are based → where you
sell today. Nothing is written until the last screen, which calls `onboarding.create` with the
name, slug and a `profile` (`BusinessProfileSchema` in
`packages/core/src/onboarding/business-profile.ts`, browser-safe via `@commerce/core/onboarding`).
`createStore` then, idempotently:

- stores `{ sells, sellsOn }` on `store.business_profile`;
- fills `store.address` with the country and state, only when the address is still empty;
- creates the starter collections for that kind of shop (`starterCollections()`), each an
  automatic collection with one "tag is `<tag>`" rule, skipping any title that already exists;
- installs the apps the router passes in `installApps`. For `sellsOn: 'shopify'` that is the
  Shopify importer, and the response's `nextPath` is `/apps/shopify-import` instead of `/`.

In invite mode the "invite-only" card carries a waitlist form (email, phone, what you sell).
`onboarding.joinWaitlist` is rate-limited to 5 tries an hour per user and per IP
(`checkRateLimit`, Redis-backed in the deployed admin, in-memory otherwise) and upserts
`signup_waitlist` by email (`joinSignupWaitlist`, `packages/core/src/onboarding/waitlist.ts`).
`bun run platform:invite <email>` sets `invited_at` on the matching waitlist row. There is no UI to
browse the waitlist yet; read it with `select email, phone, sells, invited_at from signup_waitlist`.
Migration `0073_signup_waitlist` adds the table and the `store.business_profile` column.

## The dev OTP route

Sign-in uses email OTP (Better Auth). Instead of reading the `verification` table out of
Postgres, `GET /api/dev/otp?email=<address>` (both admin and storefront ship this route)
returns the last code the server generated for that email, as `{ otp: "123456" }`.

It is **localhost only** — it answers 404 unless development mode is explicitly enabled and
the request arrived on `localhost` (or an allow-listed host via `DEV_OTP_ALLOWED_HOSTS`), and
the response is never cached. It does not exist in production builds outside that guard.
