# How Koomerce works

This section explains the whole product from top to bottom: what each part is, why it is built
that way and how it works, with a diagram for each big idea. Read it in order the first time.
The pages under Getting started, Core concepts, Building and Operations go deeper; every page
here links to them.

## What it is

Koomerce is an online-store platform for Indian D2C brands, shaped like Shopify. A merchant signs
up, gets a store, picks or imports a theme, adds products and takes orders paid by UPI, card,
net banking or cash on delivery. Couriers, GST invoices, WhatsApp messages and the rest come as
**apps** the store installs. Waimers (gaming peripherals, `www.waimers.in`) is the first store and
runs on it today; it is store number one, not a special case in the code.

Three kinds of people use it:

| Who | Where | What they do |
| --- | --- | --- |
| Shoppers | The storefront, on the merchant's own domain | Browse, buy, track, return |
| Merchants and their staff | The admin (`admin.koomerce.app`) | Run the store: orders, stock, products, theme, apps, money |
| Platform staff | The platform console in the admin (`/platform`) | Look after every store; see [Platform console](/developer-docs/operations/platform-console) |

AI apps (Claude, ChatGPT and others) can also act for a merchant over MCP, with the same
permissions and approvals as a person. See [AI and MCP](/developer-docs/how-it-works/ai-and-mcp).

## Why it is built this way

These choices come up again and again in the code. Each has a page that explains it.

1. **One database, many stores, isolated by Postgres.** Every store's rows sit in the same tables
   with a `store_id`, and row-level security shows a transaction only its own store's rows. A
   forgotten `where` cannot leak another store's data. See
   [Stores and tenancy](/developer-docs/how-it-works/stores-and-tenancy).
2. **Apps, not special cases.** Couriers, gateways, invoices and channels are packages behind a
   contract, installed per store. Core never imports a courier directly. See
   [Apps](/developer-docs/how-it-works/apps).
3. **Side effects through an outbox.** A change and the events it causes are written in one
   transaction; the worker sends the emails and runs app hooks afterwards. Nothing is lost when a
   queue is down. See [Worker and jobs](/developer-docs/how-it-works/worker-and-jobs).
4. **Cheapest setup that still holds.** One server runs the three apps, Postgres and Dragonfly;
   Cloudflare sits in front and caches store pages. Build machines never serve traffic. See
   [Deploy and operations](/developer-docs/how-it-works/deploy-and-operations).
5. **India first.** Rupees in paise, GST per GSTIN and per parcel, UPI and COD, Indian couriers,
   WhatsApp, Hindi in the admin. See [GST and invoices](/developer-docs/how-it-works/gst-and-invoices).
6. **Checks in code, not in memory.** Guardrail sweeps, a cross-store leak test and a component
   checker fail the build when a rule is broken. See
   [Testing and guardrails](/developer-docs/how-it-works/testing-and-guardrails).

## The diagrams

Every diagram in this section is an Excalidraw file in `apps/docs/public/diagrams/`. To change
one, open the `.excalidraw` file in [excalidraw.com](https://excalidraw.com) (Open, pick the
file), edit it, save it back over the same file, and run `bun run --cwd apps/docs diagrams` to
redraw its light and dark SVGs (`scripts/render-diagrams.mjs`, drawn with Rough.js, the library
Excalidraw draws with).
