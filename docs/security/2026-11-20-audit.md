# Security audit, 20 Nov 2026: checkout bots, card testing, and open-source store advisories

Two items from the 17 Nov research (`research-platform-features-nov.md`, items 9 and 10):

- **(a)** What protects checkout against bots and card testing (many small payments with stolen
  cards).
- **(b)** The problem classes from other open-source stores' 2024–2026 security advisories,
  each checked against our code.

How this was done: code reading only, plus the new vitest tests against the local test database.
Nothing touched the live site. Earlier audits are not repeated: `2026-09-28-security-audit.md`,
`audit-2026-10-06.md`, `2026-10-24-infra-pentest.md`, `2026-10-30-app-attack-catalog.md`, and the
"Known gaps found on 20 Nov 2026" list in `.claude/skills/koomerce-commerce-patterns/reference.md`.

**Result:** no critical or high findings, so no GitHub issues were opened. Two medium gaps in
card-testing protection are fixed on this branch (CT-1, CT-3). The other medium and low items are
listed with their fixes.

Paths are under `apps/storefront/src/lib/` unless stated.

## (a) Checkout bots and card testing

### What already exists

| Control | Where | Limit |
| --- | --- | --- |
| Checkout submit, per cart | `cart-actions.ts` `checkoutAction` (`CHECKOUT_CART_RULE`) | 10 / min |
| Checkout submit, per IP | same (`CHECKOUT_IP_RULE`) | 30 / min |
| Unpaid prepaid checkouts, per IP | same, `unpaid-checkout:ip` | 20 / hour, **only when the store's cap is on** |
| Unpaid checkouts, per email and phone | core `order/duplicate-checkout.ts` (`unpaidCheckoutsPerHour`, Settings → Payments) | store's choice, 0 to 50, **default 0 (off)** |
| Duplicate checkout within minutes | core `order/duplicate-checkout.ts`, `checkout-repeat.ts` | asks "order again?" |
| Retry payment, Pay online instead, I've paid | `payment-actions.ts` (`PAYMENT_RETRY_IP_RULE`) | 20 / min per IP and per order |
| UPI QR status check | `payment-actions.ts` (`QR_CHECK_ORDER_RULE`) | 8 / min per order |
| Pay a balance or invoice | `balance-actions.ts`, `invoice-actions.ts` | per IP and per order |
| Discount code guessing | `discount-actions.ts` (`APPLY_DISCOUNT_RULE`) | 20 / 10 min per IP and per cart |
| Gift card code guessing | `gift-card-actions.ts` (`GIFT_CARD_CHECK_RULE`) | 10 / min per IP; generated codes are 12 characters from a 32-letter alphabet (60 bits) |
| Sign-in code sent (email) | `account-actions.ts` `requestCodeAction` | 5 / 10 min per email, 20 / 10 min per IP, 30 s resend gap (core `accounts/auth.ts`) |
| Sign-in code checked (email) | `account-actions.ts` `verifyCodeAction` | 10 / 10 min per email, 40 per IP; **5 wrong codes lock the email** for up to an hour, counted across resends, under `FOR UPDATE` (core `verifyLoginCode`) |
| Sign-in code (SMS, WhatsApp) | `privacy-actions.ts` `requestPhoneCodeAction`, `verifyPhoneCodeAction` | per number and per IP, same lockout rules |
| Magic link, passkey, Truecaller, One Tap | `login-actions.ts` `ipAllowed` | 30 / 10 min per IP; magic link 5 / 10 min per email |
| Account enumeration | `checkout-otp.ts`, `requestLoginCode` | the same answer whether or not an account exists (sign-in by code makes the account) |
| Guest order lookup | `track-order-actions.ts`, `chat-track-actions.ts` | 10 / min per IP; needs number and email or mobile; "not found" either way |
| Honeypot | `contact-actions.ts` (`HONEYPOT_FIELD`), reviews | contact and review forms only; not on checkout |
| Turnstile | `apps/www` only (marketing site forms) | **none on storefront, checkout or sign-in** |
| Gateway side | Razorpay and Cashfree hosted card forms | the card is typed into the gateway's form; their own fraud checks apply |
| Webhook bursts | `apps/worker/src/payments.ts`, `shipments-webhook.ts` | 120 / min per IP, then the signature check |

Every per-IP limit depends on `TRUSTED_PROXY=cloudflare` and on the origin accepting only
Cloudflare's address ranges (infra pentest I-01). Without both, all shoppers share one `unknown`
bucket. This could not be checked from code.

### Gaps and fixes

**CT-1, Medium, fixed. No cap on failed payment tries per order.** "Retry payment" makes a new
gateway order every time (`retryPayment` in core `payments/attempts.ts`). The only limit was
20 per minute per order, so a bot could get about 1,200 fresh gateway orders an hour from one
order and try a different stolen card on each.

- *Fix:* new core module `packages/core/src/payments/attempt-cap.ts`. Once an order has
  **10 failed gateway attempts in the last hour**, it takes no new gateway attempt until the
  oldest failure is more than an hour old.
- *Where it applies:* `retryPayment` and COD → "Pay online instead" (both throw
  `PaymentNotRetryable`, which lands on the order page), and `placeOrder`'s
  `recordPaymentAttempt` when a checkout draft or a rewritten order is reused (it throws
  `TooManyPaymentTries`; the checkout form shows `tooManyPaymentTries` from
  `data/checkout-errors.ts`).
- *Why 10 never blocks a real shopper:* someone whose card is declined tries a few times, then
  another card or another way to pay. Gateway-to-gateway fallback inside one checkout is not
  capped, so a broken gateway never leaves an order stuck.
- *Tests:* `packages/core/src/payments/attempt-cap.test.ts`. The 11th try never reaches the
  gateway, and tries older than an hour stop counting. `apps/storefront/src/lib/checkout-errors.test.ts`
  checks that the shopper sees the message.

**CT-2, Medium, owner decision. New orders have no hourly cap by default.** A bot that opens a
fresh cart and order for each card is held only by 30 checkouts per minute per IP. The hourly
per-IP guard (20 per hour) and the per-email and per-phone cap switch on only when the store sets
Settings → Payments → "unpaid checkouts per hour" above 0, and the default is 0.

- *Recommendation:* set it for Waimers (for example 5). This also turns on the IP guard. The code
  default was not changed, because the IP guard was tied to the store setting on purpose: Indian
  mobile networks put many shoppers behind one IP.

**CT-3, Low, fixed. The checkout form's gift card list had no length limit.** `checkoutAction`
looked up every code in `form.giftCards`, so one request could check any number of codes.

- *Fix:* at most 5 cards are read (`MAX_GIFT_CARDS` in `cart-actions.ts`), and a value that is
  not an array is ignored.

**CT-4, Medium, recommendation. No challenge on storefront forms.** Turnstile protects only
`apps/www`.

- *Recommendation:* add an optional managed Turnstile check that appears only after a velocity
  trigger (for example, the second failed payment on an order, or the IP's unpaid-checkout
  guard), on the payment step and the sign-in code form. Keep it off the normal path. Size S
  to M; it needs a widget site key per store domain (Cloudflare for SaaS hostnames).

**CT-5, Info. Card tries inside one gateway order are the gateway's to stop.** Razorpay
Checkout lets the shopper try again on the same `order_id`, and its web checkout does not honour
`retry.max_count`. Our caps limit how many gateway orders a bot can get. They do not limit the
card tries inside one order. Razorpay's own risk checks cover that, so no code change is needed.

## (b) Advisory classes from other open-source stores

These advisories were collected on 20 Nov 2026 (GitHub Security Advisories, NVD, vendor posts):

- **Solidus** (Sep and Oct 2026):
  - GHSA-92gv-2pxv-7gjg: guest-checkout cards exposed through a nil-user ability.
  - GHSA-vgwx-9pm9-8qvj: another user's saved payment profile attached to a payment.
  - GHSA-qwqm-3jx5-rr8m: checkout steps skipped.
  - GHSA-87gm-56c6-255g: stored XSS in order details.
  - GHSA-3cfg-886h-22vf: unrestricted type assignment in the admin (mass assignment).
  - GHSA-qj34-2493-vx9f and GHSA-g82m-w3m9-rrwh: guest token fixation.
  - GHSA-6p7r-vx57-9gw3: return authorisation checks.
- **Saleor:**
  - CVE-2026-23499: stored XSS through HTML and SVG uploads.
  - CVE-2026-24136: unauthenticated order IDOR.
  - CVE-2026-35407 and CVE-2026-48744: authorisation bypass on channel settings and hidden objects.
- **Sylius:**
  - CVE-2026-31824: race on promotion usage limits.
  - CVE-2026-31820: cart IDOR when adding items.
  - CVE-2026-53639: payment-request IDOR.
  - A cart form that could change completed orders.
- **Vendure:** CVE-2026-25050, timing-based user enumeration.
- **EverShop:**
  - CVE-2025-12919: order IDOR.
  - CVE-2026-25993: SQL injection in URL handling.
- **Bagisto:** CVE-2025-62416 and the April 2026 batch.
- **Medusa:** no public advisory found for this period.

| Class | Seen in | Our code | Verdict |
| --- | --- | --- | --- |
| Price or total tampering from the client | general | The client sends ids only. Lines, discount, shipping (`deliveryForOrder` re-prices the quote snapshot) and payment adjustments are recomputed in `placeOrder`. | Defended. Known gap 4 (cart keeps the add-to-cart price) is already on the 20 Nov list. |
| Cart IDOR | Sylius CVE-2026-31820 | The cart id comes only from the httpOnly `wc_cart` cookie, as a UUID (`cart-cookie.ts`). Line changes are scoped to `cartLine.cartId` (core `setLineQuantity`). Recovery links are HMAC tokens (`checkout/recover/[token]`). | Defended |
| A cart form changing completed orders | Sylius | Order lines are separate rows. A converted cart replays its order and never rewrites it (`lockCartOrReplay`). `addToCart` refuses a cart that is not open. | Defended |
| Order IDOR | Saleor CVE-2026-24136, EverShop CVE-2025-12919 | Every order action goes through `accessibleOrderId` (owner session or HMAC view token). Guest lookup needs number plus email or mobile. | Defended |
| Payment-request IDOR | Sylius CVE-2026-53639 | `confirmPaymentAction` finds the payment by `providerRef`, but `confirm` checks the gateway's HMAC (Razorpay `order_id\|payment_id`) or asks the gateway. QR checks need order access. | Defended. Note: `confirmPaymentAction` has no rate limit (Info). |
| Someone else's saved payment profile | Solidus GHSA-vgwx | Shoppers have no stored cards. Store credit comes only from the session's customer (`useStoreCredit` plus `me.id`). | Not applicable |
| Checkout steps skipped | Solidus GHSA-qwqm | One server action re-runs every rule: contact, PIN code, COD rules, shipping and payment rules (`enforceCheckoutRules`). | Defended |
| Address changed after the shipping quote | Solidus (research note) | The quote is re-checked against the submitted PIN code (`deliveryForOrder`), and the PIN code is re-validated (`checkCheckoutPincode`). | Defended |
| Guest token or session fixation | Solidus GHSA-qj34, GHSA-g82m | The order view token is derived (HMAC of the order id), not chosen. A customer session is minted fresh at each sign-in (catalog A4). | Defended. `wc_cart` has no `Secure` flag (L-3). |
| Discount stacking and usage races | Sylius CVE-2026-31824 | The claim under the row lock is the truth (`claimDiscountUse`). Combined codes count each part. Concurrency test in `order/place-order.test.ts`. | Defended. Known gaps 5 and 6 stand. |
| Gift card and store credit double spend | general | The gift card row is locked `FOR UPDATE` and decremented in SQL (core `gift-cards/service.ts`). The store credit account is locked, and the balance can never go below 0 (`customers/store-credit.ts`). | Defended |
| Webhook signatures | general | Razorpay HMAC (secret required by `validateConfig`); Cashfree HMAC plus timestamp; Decentro and Snapmint fail closed; every courier adapter fails closed without a secret; SES SNS signature plus topic check plus SNS-host subscribe URL. | Defended |
| SSRF | general | User URLs go through `net/safe-fetch.ts`: media rehost, replace image by link, theme import, Shopify import, reviews, automations HTTP, Chatwoot, GrowthBook, Meilisearch, Umami, label sheets. Truecaller checks its endpoint against an allowlist. Courier base URLs are checked. | Defended (24 guard tests) |
| XSS through uploads | Saleor CVE-2026-23499 | `ALLOWED_CONTENT_TYPES` excludes SVG and HTML. Presigned uploads are bound to their content type. Theme-asset SVGs get `sandbox` CSP and `nosniff`. | Defended. Shopper photos trust the declared type (L-2). |
| Stored XSS (rich text, descriptions, order details) | Solidus GHSA-87gm | Rich text is sanitised on the server (`richtextNode` → sanitize-html allow-list). Embed blocks are sanitised. JSON-LD is escaped. Storefront CSP is nonce plus `strict-dynamic`, so injected inline scripts do not run. | Defended. Liquid has no auto-escape (L-4). |
| Open redirects | general | `safeNextPath` (core `shopper-login/tokens.ts`) refuses `//`, backslashes, control characters and other origins. `backTo` in theme actions keeps the same host only. | Defended |
| Admin role and permission checks | Saleor CVE-2026-35407 and CVE-2026-48744, Solidus | Every oRPC procedure is `can(permission)` or self-scoped (`storeProcedure`, owner checks inline). Staff cannot grant beyond their own permissions (`assertGrantable`), cannot change their own role, and only the owner hands over ownership. | Defended |
| Mass assignment | Solidus GHSA-3cfg | Every input is a zod object (unknown keys stripped). Updates spread only parsed inputs or built patches. The storefront `checkoutAction` copies named fields only. | Defended. `checkoutAction` has no runtime schema (L-5). |
| Multi-store isolation | general | Postgres RLS on `app.store_id`. The proxy strips `x-store-id` and sets it from the hostname. `/-s/` paths cannot be reached directly (`routing.ts`). Cross-store tests cover the whole router. | Defended |
| SQL injection | EverShop CVE-2026-25993 | drizzle parameters. `sql.raw` only on constants or charset-checked values (catalog C1). | Defended |
| User enumeration | Vendure CVE-2026-25050 | Sign-in by code answers the same for every email. Guest lookup says "not found" either way. | Defended |
| Secrets and codes in logs | general | Sign-in, deletion and Truecaller codes are printed only outside production (`devOtpEnabled`, `devChannels`, `mayPrintCodes`). | Defended |
| CSRF | general | Server actions use Next's origin check. Admin `/api/rpc` refuses cross-origin browser requests (`isCrossOriginBrowserRequest`). Cookies are SameSite=Lax. | Mostly defended (L-1) |

### Medium and low findings (not fixed here)

- **L-1, Low. Theme action POSTs have no Origin check.**
  - *Evidence:* `apps/storefront/src/app/-s/[storeId]/theme-actions/[action]/route.ts`. A
    cross-site top-level form post to `consent` or `localization` sets cookies on the response,
    so another site could switch a shopper's cookie-banner answer or market.
  - *Fix:* refuse the request when `Origin` is present and is not the request host (as
    `api/referral` does).
- **L-2, Low. Shopper photo uploads trust the browser's declared type.**
  - *Evidence:* review photos (`review-actions.ts` `uploadReviewPhoto`), return photos and
    inbox photos call `saveImageForProcessing` (core `media/service.ts`), which checks
    `file.type` only, not the bytes.
  - *Why it is low:* the object is served with the image type it was declared with.
  - *Fix:* check the magic bytes (JPEG, PNG, WebP, GIF, AVIF) in `saveImageForProcessing`, and
    mark the media `failed` when processing cannot decode it.
- **L-3, Low. `wc_cart` is set without `Secure`.**
  - *Evidence:* `cart-cookie.ts` `writeCartId` and the recovery route. HSTS limits the risk.
  - *Fix:* add `secure` when the request is https, as the order-view cookie does.
- **L-4, Low. Imported Liquid themes do not auto-escape.**
  - *Evidence:* the engine in core `theme-import/engine.ts` runs without `outputEscape`, as
    Shopify does. Values the shopper controls, such as `search.terms`, appear unescaped where a
    theme leaves out `| escape`. The nonce CSP stops script, so the worst case is injected HTML
    on the search page.
  - *Fix:* return escaped text from `SearchDrop.terms` (and other request-echo values), and
    check what Shopify itself outputs.
- **L-5, Low. `checkoutAction` has no runtime schema.**
  - *Evidence:* the server action's argument is typed, but a crafted call can send any JSON
    shape. CT-3 handled gift cards; other fields reach core, which validates them again.
  - *Fix:* parse `CheckoutForm` with zod at the top of `checkoutAction`.
- **L-6, Low, accepted trade-off. Sign-in lockout can be used to annoy.** Five wrong codes
  lock that email or number for up to an hour, so someone who knows a shopper's email can
  block their sign-in by code. Magic link, passkey and Google still work.
- **Info.**
  - `confirmPaymentAction` has no rate limit (the signature check makes it safe).
  - The gift card comment says 60 bits, while `2026-10-24-infra-pentest.md` says 80; 60 is
    correct for 12 characters × 5 bits, which is still far beyond guessing at 10 per minute.
    Merchant-chosen codes can be only 8 characters; the admin could warn about weak codes.
