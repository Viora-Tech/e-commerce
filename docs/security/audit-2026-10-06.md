# Security audit, 6 October 2026

Review of everything merged into `dev` since 1 October 2026 (`git log --merges --since=2026-10-01
origin/dev`, PRs #217–#284), fixed in PR `fix/security-audit-2026-10-06`. The audits of
25 and 28 September (`2026-09-28-security-audit.md`, PRs #218 and #220) are not repeated here.
Also checked, at the coordinator's request: the paused branch `origin/fix/security-audit-2026-09-28`
(5 commits, never merged), item by item against `dev` (see "The paused 2026-09-28 branch").

## Scope and method

Priority areas: Shopify theme import (zip reading, the Liquid engine and its limits, storefront
rendering, `/theme-assets`, `/theme-actions`, the Customize canvas, metafields and metaobjects
drops), server-side fetches (theme media copy and reuse, Shopify importer copies, the DNS/TLS
domain checker, `safeFetch`), authorisation and tenant isolation (staff invites, store picker,
`store.origin`, bug reports, importer Stop/Retry, domain connect/verify), secrets and config
(#245 blank-means-unset, logging of codes and links, error messages), and the multi-tenant
items (one store's work starving the others, leak-test coverage of the new tables). The AI v2
assistant (#237) had a lighter pass (approval flow and permission checks).

Severity, as in the earlier audits: **Critical** = account takeover, data of others or money
without a precondition an outsider cannot meet; **High** = the same with a realistic
precondition, secret theft, or one tenant taking the shared servers down for everyone;
**Medium** = harm needing staff access or unusual conditions; **Low** = defence in depth.

## Fixed

### A-00 Critical: any order's page by its number

- **Where**: `apps/storefront/src/lib/cart-actions.ts` `retryPaymentAction(orderNumber)` and
  `checkQrPaymentAction(orderNumber)`, `apps/storefront/src/lib/balance-actions.ts`
  `payBalanceAction(orderNumber)`. Each looked the order up by its number only and redirected to
  `thankYouPath(number, orderViewToken(orderId))`, a freshly signed token, on every exit
  (including the rate-limited one).
- **Exploit**: order numbers are sequential. Call the server action (its id is in every
  storefront page's JavaScript) with `N`; the 303 points at `/checkout/thank-you/N?t=<valid
  token>`, which shows the shopper's name, delivery address, phone, items and totals. Repeat for
  every `N`. `checkQrPaymentAction` also told whether any order was paid and made us call the
  gateway for it. Found on the paused 09-28 branch (commit `bc15f9cf`, "order-view token only for
  owners"), never merged; PR #218 did not include it.
- **Fix**: `canViewOrder` (`core/src/preorder/balance-link.ts`) and `viewableOrderId`
  (`core/src/order/view-access.ts`): the signed-in owner, or a view token minted for this exact
  order. `lib/order-access.ts` `accessibleOrderId` runs it before any token is minted; the
  actions take the page's `viewToken` (thank-you, account order, pay-balance pages and the UPI QR
  pass it); a stranger lands on the untokened page, which shows nothing. The thank-you page
  reuses an incoming token only when it is valid for that order.
- **Tests**: `core/src/preorder/balance-rules.test.ts` `canViewOrder`;
  `apps/storefront/src/lib/order-access.test.ts` (owner, token, foreign token, stranger;
  `payBalanceAction` sends a stranger to the untokened page).

### A-01 High: theme zip bomb

- **Where**: `packages/core/src/theme-import/archive.ts` (fflate `unzipSync` with a filter on the
  declared sizes). fflate inflates into a buffer of the declared size and keeps decompressing
  past its end (writes are dropped), so the work is the real expansion, not the declared one.
- **Exploit**: any staff member with `online_store.write` (any merchant) uploads a 50 MB zip
  whose one entry says 1 KB and inflates to ~50 GB: measured 4.7 s of CPU per 200 KB of such a
  zip, so ~20 minutes of a blocked event loop on the shared API server per request, for every
  store.
- **Fix**: the zip's central directory is read by hand (bounds-checked), and every entry is
  inflated with the streaming `Inflate` in 16 KB steps against what it declared; the first byte
  past it stops the read (`TOO_BIG`). Declared sizes are still capped as before, so the real
  work is bounded by 120 MB. Encrypted and unknown-method entries are skipped.
- **Tests**: `theme-import/security.test.ts` "refuses an entry that inflates past what it
  declares" (both a 1 KB and an honest-looking claim; under 500 ms) and "still reads an honest
  zip"; the existing `engine.test.ts` archive cases.

### A-02 High: public SETTINGS_SECRET in production

- **Where**: `packages/config/src/env.ts`. `SETTINGS_SECRET` defaults to
  `dev-only-settings-secret`; since #245 a blank value counts as unset, and
  `deploy/docker-compose.prod.yml` passes `${SETTINGS_SECRET}` (blank when the key is missing).
- **Exploit**: with the key blank or missing, every gateway, courier and storage secret is
  encrypted, and every view, balance, preview, newsletter and sign-in hand-off token signed, with
  a value that is in the repository. Anyone could forge an order view token (A-00's data) or a
  theme preview for any store, and decrypt a stolen settings row.
- **Fix**: `loadEnv` refuses `NODE_ENV=production` with the default (so with a blank or missing
  key): "SETTINGS_SECRET is required in production".
- **Owner action before deploying**: confirm the production app has `SETTINGS_SECRET` set
  (key name only; do not paste the value anywhere). If it does not, the apps will refuse every
  request after this deploy, which is the intended failure.
- **Tests**: `packages/config/src/env.test.ts` "refuses a missing or blank SETTINGS_SECRET in
  production".

### A-03 High: render time held the shared servers

- **Where**: `theme-import/engine.ts` (`renderLimit: 20_000` per `renderSync`), `render.ts`
  (every pass, static section and theme block a fresh 20 s; nothing per page), the layout split
  in `render.ts` (`/<head\b[^>]*>([\s\S]*?)<\/head>/`, `OWN_HEAD`).
- **Exploit**: a theme section `{% for a in (1..100000) %}{% for b in (1..100000) %}{% endfor
  %}{% endfor %}` holds the storefront's event loop 20 s per pass, up to five passes, per
  section, per request: a handful of requests to one store's page stops every store. The same in
  Customize holds the API (60 sections per call). A layout of `<head<head<head…` with no `>`
  made the split quadratic.
- **Fix**: `renderBounded` (engine.ts) replaces every `renderSync`: 2 s per pass, 6 s for all
  renders of a page context (the budget lives on the context, nested renders count once), and a
  4 M character output cap (a capped emitter). The layout split uses forward-only searches
  (`openTag`, `closeTag`, `withoutOwnHead`) and attribute text is capped at 10 k.
- **Tests**: `security.test.ts` "render budgets" (runaway loop, page budget then nothing more,
  output flood) and "splits a layout built to make patterns backtrack"; `engine.test.ts`.

### A-04 Medium: CSP nonce on scripts that came in with data

- **Where**: `apps/storefront/src/lib/liquid-theme.ts` `withNonce` added the nonce to every
  `<script` in the rendered HTML (sections, head, body parts, the section endpoint).
- **Exploit**: a staff role with only products or content access (or an imported Shopify
  product) puts `<script>…</script>` in a product title, a content entry or a section setting; a
  theme that prints it unescaped (common, Shopify does not auto-escape) runs it on the storefront
  with a valid nonce: shopper sessions act through it, checkout pages can be framed and read.
- **Fix**: nonces are added at parse time to the theme's own source only: `nonceThemeScripts`
  (bundle.ts) writes the `{% commerce_script_nonce %}` tag after every `<script` in markup
  (never inside `{% %}`, `{{ }}` or `{% raw %}`), and the tag prints the request's nonce. Output
  is never re-scanned, so data gets none and the CSP blocks it. `withNonce` is gone.
- **Tests**: `security.test.ts` "nonces only on the theme's own scripts" (source script and
  snippet get it, a product title's script does not; tags and raw blocks untouched).

### A-05 Medium: canvas sanitiser on the admin origin

- **Where**: `packages/api/src/services/theme-import.service.ts` `stripScripts` (two regexes).
- **Exploit**: `<img src=x onerror=…>`, `<img/onerror=…>`, `<script src=…>` without an end tag,
  `<a href="javascript:…">`, `<iframe srcdoc>`, `<meta http-equiv=refresh>` all reached the
  Customize iframe, which shares the admin's origin. The nonce CSP blocks most of it in current
  browsers; older ones fall back to `'unsafe-inline'`; meta refresh is not script.
- **Fix**: `sanitizeCanvasHtml` (`packages/blocks/src/canvas-sanitize.ts`, `sanitize-html`):
  every element and attribute a theme needs for its look stays; script and plugin elements,
  frames, `meta`, `base`, `on*` handlers, `srcdoc`, non-web URLs and SVG animations of URL
  attributes go; raw-text elements holding `<` are dropped (no `<svg><style>` mutation). Used
  for the head, the body parts and every section (`canvasSafeHtml` in core).
- **Tests**: `packages/blocks/test/canvas-sanitize.test.ts`.

### A-06 Medium: theme import downloads and the live page

- **Where**: `theme-import/import.ts`, `import-media.ts`.
- **Exploit**: the theme names the images and the merchant names the host. 10,000 image names
  on a host that answers slowly hold the request, its database transaction and connection for
  hours (20 s × 4 sizes per image, six at a time); a few such imports exhaust the pool for every
  store. The "live page" (8 MB from that host) was read with `[\s\S]*?` patterns that are
  quadratic on `<video<video…`.
- **Fix**: `THEME_MEDIA_LIMITS` (300 images, 20 videos, 3 minutes); the rest is listed as not
  copied in the report. `liveVideosIn` uses forward-only `indexOf` and patterns on one element of
  at most 4 k. `themes.import.shopify` counts against the store's `heavy('import')` budget.
- **Tests**: `security.test.ts` "reads the live page's videos, and a page built to backtrack,
  quickly", "stops at the count and at the deadline".

### A-07 Medium: admin API CSRF from the same site

- **Where**: `apps/admin/src/app/api/rpc/[[...rest]]/route.ts`. oRPC accepts multipart bodies (a
  "simple" request, no CORS preflight), and Better Auth's session cookie is `SameSite=Lax`, which
  rides on cross-origin requests within one site.
- **Exploit**: the deploy example runs the admin at `admin.waimers.in` and a store at
  `waimers.in`. Theme JavaScript on that storefront (A-04, or an imported theme) posts a form to
  `admin.waimers.in/api/rpc/staff/invite` and the merchant's session invites the attacker.
- **Fix**: the route refuses requests whose `Sec-Fetch-Site` is anything but `same-origin` or
  `none` (`lib/request-site.ts`); the admin only calls its API from its own pages. Server code
  and non-browser callers send no such header and carry no browser cookie.
- **Tests**: `apps/admin/src/lib/request-site.test.ts`.

### A-08 Medium: sign-in codes and invite links in production logs

- **Where**: `apps/admin/src/lib/auth.ts`: without the platform email transport the code (and the
  invite accept link) was `console.log`ged, in production too.
- **Fix**: `mayPrintCodes()` (dev-otp.ts) is false in production; there the send fails with the
  plain "Could not send…" message and the log says only that email is not set up.
- **Tests**: `apps/admin/src/lib/dev-otp.test.ts` `mayPrintCodes`.
- **Owner check**: production must have the platform email account configured
  (`SENDER_EMAIL_PROVIDER=ses` and the SES keys), or admin sign-in now says the code could not
  be sent instead of logging it.

## Design items (issue-ready, not fixed here)

**D-01 (Medium) Theme JavaScript shares the origin of checkout and the shopper account.**
Imported themes run their own scripts on the store's origin, which also serves `/checkout`,
`/account` and the order pages. The checkout drops the theme's layout, but a theme script on any
other page can open a same-origin frame or `fetch` those pages and read them, and act as the
signed-in shopper. Merchants upload their own themes (and soon third-party ones). Proposal: serve
checkout and account on a separate origin (Shopify's model), or at least send
`Cross-Origin-Opener-Policy`/`frame-ancestors 'none'` on checkout and account pages and review
which account actions need a fresh confirmation.

**D-02 (Medium) Admin on the same registrable domain as a storefront.** The deploy example
pairs `admin.waimers.in` with the `waimers.in` store. A-07 closes the API, but any other
cookie-bearing admin route added later inherits the same-site exposure. Proposal: move the admin
to a domain no store uses (e.g. `admin.vextro.app`), and add a sweep that new admin POST routes
call `isCrossOriginBrowserRequest`.

**D-03 (Low) Custom domain squatting.** A pending domain holds the hostname forever; the real
owner is told "connected to another store" and must ask support. Proposal: expire pending claims
after 14 days, or let a store that proves the TXT record take a hostname held only by a pending
claim.

**D-04 (Low, owner decision) Bug report screenshots.** "Report a bug" stores a screenshot of the
admin page (which can show customers' names, addresses and phones) at a permanent public URL in
the store's bucket, links it from a GitHub issue with the reporter's name and email, and erasure
never removes it. Decide: private repository only, signed short-lived URLs, and adding
`stores/<id>/bug-reports/` to erasure and store deletion.

**D-05 (Low) AI action approve/undo race.** `approveAction` and `undoAction`
(`api/src/services/ai/assistant/service.ts`) read the row, then update it without a lock: two
quick approvals run the change twice (a discount created twice; price changes are protected by
their compare-and-set). Fix: `.for('update')` in `ownOpen` and in `undoAction`'s read, with a
DB test of two parallel approvals.

**D-06 (Low) Liquid drops and unpublished content.** `collections[handle].products` lists the
products of a draft collection (the products themselves are active), and pages with a future
`published_at` are shown. Fix: `eq(collection.status, 'active')` in `collectionProducts` and
`lte(page.publishedAt, now)` in `page`, with the cross-store/visibility tests.

**D-07 (Low) Request body size.** `/api/rpc` reads the whole body before Zod sees the 50 MB
limit (`themes.import.shopify`), and nothing limits other procedures' bodies. Proposal: a body
size limit in Traefik/Next for `/api/rpc` (60 MB for the import path, 1 MB elsewhere).

**D-08 (Low) Output inside `{% capture %}` loops** grows within the 2 s render budget only; the
4 M output cap applies to what reaches the page. Acceptable today; revisit if memory alerts show
render spikes.

**D-09 (Info) Worker keeps running after uncaught exceptions** (`apps/worker/src/index.ts`, #277).
A library throw outside a job is logged and ignored, leaving possibly half-done state in that
process. Prefer: report, then exit so the container restarts, once the importer's video copy no
longer throws there.

**D-10 (Info) DNS rebinding in `safeFetch`** stays the accepted residual from S-06 (checked
address, then a second lookup at connect).

## Reviewed and fine

- **Zip paths**: `safeThemePath` refuses `..`, absolute paths, drive letters and NUL; only theme
  folders and known types are kept; nothing is executed.
- **Liquid sandbox**: snippets come from memory (`templates`, no file system); `ownPropertyOnly`;
  drops keep their cache and data in `#private` fields; `_rt` exposes only the nonce and harmless
  callbacks; no filter touches the network, the disk or `process`.
- **Custom data (#278)**: only definitions with storefront access, active entries and published
  targets; every read under the store's RLS; extra-field owners come from drops the store's own
  catalogue built.
- **Storefront theme routes**: `/theme-assets` checks the theme UUID and a flat file name, serves
  only theme file types with `nosniff`, sandboxes SVG; `/theme-actions` takes the store from the
  hostname, clamps quantities, posts back only to the same host.
- **New tables** (`theme_file`, `theme_import`, AI tables, import snapshots) are under
  `apply_store_rls()`; the cross-store leak test seeds every store table automatically.
- **Staff invites (#248)**: every invite action loads the invitation for this store's
  organization first; a role above the inviter's is refused; the email goes through the platform
  account. **Store picker (#251)**, **`store.origin` and `storefrontOriginFor` (#254)**: the
  primary domain counts only when active (TXT-verified).
- **Domain checker (#250)**: TXT token always required; Cloudflare-proxied domains only with the
  TXT; lookups and the TLS handshake time out.
- **Importer (#249, #270, #277)**: shop domain locked to `*.myshopify.com`, so bulk results come
  from Shopify; every media copy through `safeFetch` with caps; Stop/Retry load runs under RLS and
  remove only this store's job; per-store queue fairness unchanged.
- **Bug reports (#271)**: signed-in members only, 10 an hour per person, secrets scrubbed, the
  GitHub token only in the header, production refuses to start without it.
- **#245 blank-means-unset**: apart from A-02, every other default is safe when blank
  (`TRUSTED_PROXY=none`, `MERCHANT_SIGNUP_MODE=invite`, `DOMAIN_PROVIDER=dev`).
