# Apps audit, Phase 1b group 3 (12 Nov 2026)

Roadmap Phase 1b, group 3: the payment apps not in use yet. Cashfree and Decentro. Razorpay
(marked `tested: true`) was the reference to compare with.

**What this audit is.** A code-level read plus the local tests, on `origin/dev` at `cb0c6331d`.
No live store, no real provider account and no provider call was used (Cashfree and Decentro
were faked). So "works end to end" is not proven here: each app ends with a short live check the
owner runs, **sandbox keys first**. **No manifest was set to `tested: true`.** Flip it after the
live check passes.

What was checked for each feature: is there a test; webhook signature or token checked in
constant time on the raw body; webhooks de-duplicated (and does the id survive status changes);
money in integer paise with no float drift; currency; status moves match Razorpay's (the shared
forward-only `nextPaymentStatus`); refunds capped at what was captured; timeouts and retries on
outside calls; secrets kept out of logs and errors; store scoping; what a shopper can see of a
gateway error.

## Summary

| App | Tests (before → after) | Bugs found and fixed | Ready for `tested: true` after the live check? |
| --- | --- | --- | --- |
| Cashfree | 59 → 67, all pass | 4 (#1593, #1594, #1595, #1596) | Yes, once the fix PR is deployed and the sandbox check passes |
| Decentro | 41 → 44, all pass | 1 (#1597) | Yes for UPI QR payments and refunds to source; see the gaps (refund status, payouts not wired) |

Shared platform code read and found sound for both: the webhook route (`apps/worker/src/payments.ts`:
raw body, lower-cased headers, per-IP rate limit, store id from the URL, store scoped through
`withStore`); `handlePaymentWebhook` (stores each event once on store + provider + event id,
duplicates acknowledged without being applied); `applyPaymentStatus` (order then payment row
locks, forward-only status, a capture on a cancelled or already paid order kept and flagged
"refund needed"); `refundPayment` (payment row locked, refunds capped at captured minus earlier
refunds that did not fail, refund key `rf_<payment>_<already refunded>`). Gateway error text is
stored on the payment for the merchant; the storefront shows the shopper only "failed" or "this
way to pay is unavailable", never the gateway's words.

Fix PR (into `dev`, not merged): one PR for all five issues and this audit; its number is in each
issue.

## Cashfree (`packages/payments-cashfree`)

**Features.** Connect page (App ID, Secret key; Test or Live set by the admin; the webhook URL
is written for the merchant and sent as `order_meta.notify_url` when it is https) with Test
connection (a read-only lookup of a made-up order: 404 means the keys work); checkout as
Cashfree Checkout in a modal (`client` session: payment session id, sandbox or production);
UPI, cards, netbanking, wallets and pay later / EMI, limited and ordered by the store's method
settings (`order_meta.payment_methods`); status check (`GET /orders/{id}`, then its payments: a
success anywhere wins, else the latest try decides); webhooks: payment success, payment failed,
charges (Cashfree's fee once worked out), refund status (success, cancelled, failed); fee sync
(`fetchCharges`: method from the payment, fee from the order's settlement, a fee the shopper bore
is not the merchant's); full and partial refunds from the order page (Cashfree refunds per
order, so the order id is sent with our refund key as `refund_id`); EMI app links to it. Not
built: Cashfree payment links (the store's own pay link is used), settlements reports,
authorise-then-capture (no `capture`), payouts.

**Coverage.** Good before: order id format, order body (rupees, tags, methods, notify URL),
phone rule, every status mapping, refunds, every webhook kind, signature and replay window,
connection test, config, sandbox vs production hosts, fees. New (faked HTTP): refund webhook ids
per status, timeouts, refund retry after a lost reply, draft order ids.

**Code read.**
- Signature: base64 HMAC-SHA256 of `x-webhook-timestamp + rawBody` keyed with the secret key,
  compared with `safeEqual` (constant time) on the raw body; timestamps more than 15 minutes off
  are refused. Missing headers fail closed.
- Money: paise to rupees with `toFixed(2)`, rupees back with `Math.round(x * 100)`: exact for
  two-decimal amounts. Currency is INR only (the contract's type).
- Status moves: the same as Razorpay's. A failed try leaves the Cashfree order open; a later
  success in the same order still captures (allowed by `nextPaymentStatus`). Cashfree has no
  browser signature, so "confirm" asks Cashfree for the status of our own server-made order: a
  shopper cannot fake a capture, and the amount is the order's.
- Order tags carry our order id and attempt key, so a webhook finds the attempt even if saving
  the Cashfree reference failed. Tags can only be set with the secret key.
- Idempotency: `x-idempotency-key` is a UUID derived from our attempt key, so a retried create
  gets the same Cashfree order.
- Secrets: the secret key is `secret: true`, sent only as a header, never put in an error.
- Store scoping: the webhook URL carries the store; the signature uses that store's key; the
  attempt is looked up inside that store.

**Bugs fixed.**
- #1593: one refund's status webhooks (PENDING or ONHOLD, then SUCCESS or CANCELLED) shared one
  event id, so the final one was acknowledged as a duplicate and never applied. A cancelled
  refund kept counting as money returned. Now the status is part of the id.
- #1594: Cashfree calls had no timeout; a stuck connection could hang the payment start, the
  unpaid-order expiry check, the fee sync or a refund. Now 15 s.
- #1595: a refund whose reply was lost (Cashfree did refund) could not be retried: Cashfree
  refuses the reused `refund_id` and nothing was recorded. Now the retry looks the refund up by
  that id and records it when the amount matches; any other refusal still shows as an error.
- #1596: checkout drafts (no order number yet) got Cashfree order ids that differed only in 8 hex
  characters of our id, so on a busy store two drafts would sooner or later collide and the second
  shopper could not pay. Drafts now use `d<draft number>_…`. This matters more once drafts are the
  default checkout (open PR "keep unpaid checkouts as drafts by default").

**Gaps (not fixed, for the owner).**
- No `return_url` is sent (the platform does not pass one to any gateway). In the modal this is
  fine; if Cashfree ever takes the shopper to a full-page bank step, Cashfree's own page is where
  they end up, and the order is still confirmed by the webhook or the status check.
- In the storefront, a payment Cashfree's modal reports as failed shows "closed" (Try again)
  rather than "failed". Cosmetic.
- A shopper needs a 10-digit phone (Cashfree requires one); without one the payment cannot
  start. Not checked here whether every checkout setup asks for a phone.
- Shared with Razorpay (core, not this app): any `refund.processed` webhook, even for a partial
  refund, moves the payment's own status to "Refunded". Refund totals and the order's payment
  status come from the refund rows, so amounts stay right; only the attempt's label is off. Worth
  a look for both gateways.

**Owner's live check (sandbox keys first, then live).**
1. Cashfree dashboard, Developers: copy the **Test** App ID and Secret key; Apps > Cashfree >
   Connect, choose Test; Test connection says "Connected".
2. In Cashfree, Developers > Webhooks: add the webhook URL shown on the Connect page, version
   with Payment, Refund and Charges events. Send Cashfree's test webhook; it is accepted (no
   "bad signature" refusal in the worker log).
3. Turn Cashfree on for checkout. Place a test order; pay with Cashfree's test UPI ID (success);
   the order is paid within seconds and the payment shows the Cashfree payment id.
4. Place another; fail it with the test failure UPI ID; the order stays unpaid, Try again opens a
   fresh modal; pay successfully; the order is paid once.
5. Test card (Cashfree's test card, OTP page) and a netbanking test bank: both mark the order paid.
6. Refund part of the paid order from the order page; Cashfree shows the refund; when its status
   turns Success, the refund on the order says processed. Refund the rest; the total refunded
   equals the payment, and a third refund is refused.
7. With unpaid checkouts kept as drafts, pay a draft checkout; the Cashfree order id starts with
   `d` and the draft becomes an order.
8. Next day: the payment's fee appears (charges webhook or fee sync), with GST.
9. Switch to Live keys, Test connection, one small real UPI payment and a full refund.

## Decentro (`packages/payments-decentro`)

**Features.** Connect page with two key sets (staging and live: Client ID, Client secret,
Consumer URN, Callback secret, Payouts consumer URN) and Test connection (a made-up reference:
"no transaction" means the keys work); UPI only: one dynamic UPI link per attempt (`upi_qr`
session; drawn as a QR on a computer, opens the UPI app or the Google Pay / PhonePe / Paytm /
CRED buttons on a phone), 30-minute expiry, ₹5 minimum; the thank-you page asks Decentro whether
an open QR was paid (no wait for the callback); "Get a new QR" after expiry settles the old one
first; status callback (Decentro's terminal transaction callback); status check for expiry and
reconcile; full and partial refunds to the payer's UPI ID; refund by UPI payout from a funded
Decentro account (`refundViaPayout`, built but not used by any screen yet).

**Coverage.** Good before: reference ids both ways, status mapping, link creation and hosts,
amount floor, FAILURE replies, status check, callbacks (success, failed, expired, held, released,
auto-refunded, deemed, disputed), the token check, refunds with duplicate key, payouts, connection
test, config. New (faked HTTP): timeouts on a status check, a payout and the connection test.

**Code read.**
- Callbacks are not signed by Decentro. The adapter fails closed without a Callback secret,
  compares the token (`x-webhook-token`, or `Authorization: Bearer`) with `safeEqual`, and
  requires the callback's `consumer_urn` to be this merchant's. The event id is Decentro's first
  callback id, so its retries are stored once.
- Decentro wants `{ "response_code": "CB_S00000" }` in our reply or it retries; the route adds it.
- Money: rupees with two decimals out, `Math.round(x * 100)` back; strings handled.
- Amount check: the callback's paid amount goes through the same "must cover the attempt" check
  as Razorpay's. DISPUTED_AMOUNT and DEEMED stay pending, never captured.
- Refund idempotency: the refund key is the refund's `reference_id`; a repeat is refused by
  Decentro as a duplicate and the adapter reports the first refund. Payouts the same.
- Secrets: Client secret and Callback secret are `secret: true`; never put in errors.

**Bug fixed.**
- #1597: Decentro calls (collections and payouts) had no timeout. Now 15 s.

**Gaps (not fixed, for the owner).**
- Refund status after the first answer is not followed: Decentro's refund callback format is not
  documented, so refund updates are ignored, and no job asks again. A refund Decentro accepts
  stays "pending" on the order (it still counts as refunded); one Decentro later fails is never
  noticed. Needs Decentro's refund callback sample or a status poll.
- `refundViaPayout` is not wired to the refund dialog, so a UPI payout refund (for a payment that
  cannot be refunded to source) has to be done in Decentro's dashboard.
- An order whose payment sits in DEEMED or DISPUTED_AMOUNT is expired (cancelled) by the unpaid
  order job like any unpaid one. If Decentro later says SUCCESS, the money is kept and flagged
  "refund needed", the same rule as every gateway.

**Owner's live check (staging keys first, then live).**
1. Apps > Decentro > Connect, staging keys and Consumer URN; Test connection says "Connected".
2. Ask Decentro support to send the callback to the URL shown on the Connect page with the
   header `x-webhook-token: <Callback secret>`. Until that is done, payments only turn paid
   through the thank-you page's own check.
3. Turn Decentro on for checkout. Place a test order of at least ₹5; on a computer a QR shows;
   pay it with Decentro's staging UPI simulator; the order turns paid without a refresh.
4. On a phone, the Google Pay / PhonePe buttons open the app with the amount filled in.
5. Let a QR expire; "Get a new QR" gives a new one; paying it marks the order paid once.
6. Refund part of a paid order; Decentro shows the refund; refund the rest; a third is refused.
7. The callback is accepted (no "bad token" refusal in the worker log); Decentro does not
   retry it (our reply carried `CB_S00000`).
8. Live keys: one small real UPI payment and a full refund.
